# Plan Mode (플래닝 모드) 스킬 가이드

본 스킬은 복잡하거나 구조적인 변경이 필요한 작업에서 즉각적인 코드 수정으로 인한 부작용을 방지하고, 철저한 설계 검토 및 체계적인 단계별 구현을 진행하기 위한 워크플로우 규약입니다.

---

## 1. 계획서 작성 규칙 (`docs/plans/`)

1. **저장 위치 및 파일명**:
   - 모든 계획서는 반드시 `docs/plans/{YYYY-MM-DD}_{제목}.md` 포맷으로 작성합니다.
   - 예시: `docs/plans/2026-09-07_add_game_mode.md`
2. **계획서 필수 섹션**:
   - **1. 목적 및 배경 (Background & Goals)**: 작업의 필요성 및 해결하고자 하는 문제
   - **2. 코드 분석 및 원인 규명 (Analysis)**: 현행 코드 구조 및 수정 대상 분석
   - **3. 상세 개선/구현 계획 (Detailed Changes)**: 모듈별, 파일별 변경 명세
   - **4. 기능별 커밋 계획 (Commit Plan)**: 단위 기능별 분할 커밋 메시지 목록
   - **5. 검증 계획 (Verification Plan)**: 빌드, 단위 테스트, 수동 시나리오 검증
   - **6. 위키 갱신 계획 (Wiki Sync Plan)**: 작업 종료 후 반영할 `20_Wiki/` 문서
   - **7. 열린 질문 (Open Questions)**:
     - **계획서 리뷰의 마지막에는 항상 사용자에게 피드백을 요청하는 열린 질문을 작성합니다.**
     - **확인이나 상의가 필요한 질문 사항이 없다면 "열린 질문: 현재 추가 문의 사항은 없습니다."라고 명확하게 밝힙니다.**

---

## 2. 구현 착수 게이팅 규칙 (Gating Rules - 엄격한 2단계 조건)

에이전트는 다음 **2가지 조건이 모두 충족**되기 전까지는 소스 코드 수정, 파일 생성, 빌드/배포 등 구현 작업을 **절대로 시작해서는 안 됩니다.**

```text
┌────────────────────────────────────────────────────────┐
│               구현 착수를 위한 필수 2조건              │
│                                                        │
│  1. 해당 계획서의 리뷰가 모두 완료되었는가?            │
│  2. 사용자가 직접적으로 "구현"이라는 문구를 썼는가?    │
└────────────────────────────────────────────────────────┘
```

1. **계획서 리뷰 완전 완료 전 구현 금지**:
   - 계획서가 작성된 후 사용자의 검토, 피드백 반영, 수정 계획 합의가 끝나기 전까지는 일체의 구현 코드를 작성하지 않습니다.
2. **사용자의 직접적인 "구현" 문구 대기**:
   - 사용자가 "좋아", "진행해", "확인했어" 등의 모호한 표현을 쓰더라도, 직접적으로 **"구현"**(예: "구현 시작해줘", "이제 구현해봐" 등)이라는 단어를 사용하기 전까지는 구현을 시작하지 않고 대기합니다.

---

## 3. 구현 위치 결정 (develop 최신 커밋 기반 분기 여부 질의)

사용자의 "구현" 지시가 확인되어 구현에 착수할 때:

1. 에이전트는 **항상 `develop` 브랜치의 최신 커밋을 기반으로 새 브랜치를 생성하여 구현할지 여부**를 사용자에게 먼저 질문해야 합니다.
   - 질의 예시: *"구현을 시작하기 전에, 최신 `develop` 브랜치 커밋을 기준으로 새 브랜치를 생성하여 작업할까요? 아니면 현재 브랜치(혹은 다른 브랜치)에서 계속 진행할까요?"*
2. **사용자의 응답에 따라 구현 위치(베이스 브랜치 및 작업 브랜치)를 결정**하고 브랜치를 생성/전환한 뒤 비로소 실제 구현을 시작합니다.

---

## 4. 구현 단계 규칙: 기능별 분할 커밋

1. 구현 중에는 모든 작업을 한 번에 커밋(대량 일괄 커밋)하지 않습니다.
2. 계획서 4섹션의 '기능별 커밋 계획'에 따라, 논리적/기능 단위로 분할하여 개별 커밋합니다.
   - 예:
     - `feat : GameDao 신규 쿼리 추가`
     - `feat : GameRepository 구현체 변경`
     - `feat : GameViewModel 상태 머신 연동`
     - `test : GameViewModel 단위 테스트 추가`

---

## 5. 작업 종료 규칙: 위키 갱신

1. 코드 구현 및 빌드/테스트 검증이 완료된 후, 작업 내역을 프로젝트 지식 그래프에 동기화합니다.
2. `20_Wiki/Concepts/` 또는 `20_Wiki/Entities/`에 신규/수정된 아키텍처 문서를 작성 또는 병합합니다.
3. `20_Wiki/Indexes.md`를 최신 상태로 갱신합니다.
